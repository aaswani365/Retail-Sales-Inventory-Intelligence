## 1. Purpose and scope

This is the **implemented** SQL execution plan, replacing the obsolete pre-build numbering proposal. It records the actual 41-file sequence (orchestrator `00` plus numbered scripts `01–40`), repository-relative paths, dependencies, responsibilities, execution conditions, rerun constraints, and release gates. It does **not** instruct users to rerun a completed build. SQL Server database changes, validation results, and Power BI visual behavior must be independently verified in the target environment.

The solution uses **one SQL Server database**, with normalized operational schemas (`ref`, `core`, `sales`, `inventory`), audit objects (`audit`), and a separate dimensional/reporting schema (`analytics`). Synthetic data is generated by **T-SQL**, not by a Python ETL pipeline.

| `PeriodStartDate` | `2023-07-01` | Configured generation period start |
| `PeriodEndDate` | `2026-06-30` | Configured generation period end |
| `EnableDataReset` | `0` | Data reset disabled by default |
| `SqlRoot` | `..` | SQLCMD path from `00_orchestration/` |

**Safe usage on a fresh LOCAL/DEV/TEST database only:**

1. Place all 41 canonical scripts in the folders shown in Section 3.
2. Open the runner in SQL Server Management Studio, enable **Query → SQLCMD Mode**, and review the target SQL instance and parameters.
3. Execute only in an approved nonproduction environment, with a fresh database or after following the per-script reset/rerun policy.
4. Inspect the validation and completion outputs; a printed success message is not a substitute for examining errors and validation records.

From `sql/00_orchestration/`, the source-provided command-line example is:

```powershell
sqlcmd -S <server> -E -b -i 00_Run_Full_Build.sql
```

`<server>` is a placeholder for the operator's instance; do not paste angle brackets literally. The `-E` option uses Windows integrated authentication. Do **not** run the full build simply to check folder paths on a completed database. Do **not** run against production.

## 6. Dependency and rerun controls

### 6.1 Dependencies

- **Foundation:** `01 → 02 → 03 → 04 → 05–09`; the runner calls all foundation scripts in order. Script 09 enforces the absence of DML triggers under the project's governance policy.
- **Generation:** `10 → 11 → … → 21`; operational records are connected and should not be regenerated out of sequence.
- **Analytics:** `22 → 23 → 24 → 25 → 26`; dimensional validation (`26`) is a prerequisite for the downstream analysis workloads.
- **Analysis:** `27 → … → 35`; these are read-only business investigations, with temporary tables as required.
- **Release:** `36 → 37 → 38 → 39 → 40`; data-quality acceptance precedes benchmarks; the eight Power BI views are built before their SQL-side validation; deployment health is last.

### 6.2 Rerun restrictions

| Scope | Policy from the implemented scripts |
|---|---|
| Foundation `01–09` | Generally rerunnable; scripts preserve existing approved objects or use `CREATE OR ALTER` / validation |
| Reference/master data `10–15` | Generally rerunnable using stable keys/codes and controlled upserts |
| Opening inventory `16` | Rerunnable **only until** downstream non-opening inventory movements exist |
| Sales orders `17` | Rerunnable **only until** downstream lifecycle, payment, return or sales-movement data exists |
| Order lifecycle `18` | Rerunnable **only until** payments, returns or downstream inventory facts exist |
| Payments `19` | Rerunnable **only until** returns, refunds or downstream inventory facts exist |
| Returns/refunds `20` | Rerunnable **only until** downstream inventory movements exist |
| Inventory movements `21` | Rebuilds non-opening movements deterministically; review downstream dependencies before use |
| Dimensions `22` | Rerunnable **before** analytical fact tables are created |
| Facts `23` | Rebuilds analytical facts; treat as a controlled reload, not a harmless read-only operation |
| Analytics views/indexes `24–25` | Rerunnable under their source-defined object policies |
| Validation `26`, `36`, `39`, `40` | Rerunnable, but each creates an additional audit validation run |
| Business analysis `27–35`, benchmark `37` | Read-only against persistent business data; may use session-scoped temporary tables |
| Power BI reporting views `38` | Rerunnable using `CREATE OR ALTER VIEW`; review downstream semantic-model contracts |

**Rule:** `Rerunnable: Yes` in a script header is conditional where stated; it is not permission to rerun the entire project on a populated environment. Avoid manual data deletion or forced resets without a documented backup and impact review.

## 8. KPI definitions, grains and date attribution

The implementation deliberately aggregates facts at their natural grains before combining them, to avoid multiplying amounts through many-to-many transactional joins. For example, payments are measured by **payment attempt**, returns by **returned order item**, refunds by **refund event**, and sales by **order item** (with order-level measures controlled separately).

- **Revenue:** delivered-line recognized pretax revenue; completed refunds reduce net revenue according to the applicable report's date-attribution policy.
- **Profit:** recognized gross profit and return/COGS reversals must be interpreted using the implemented query's calculation scope.
- **Sales demand/cancellations:** order-date attribution; realized sales typically use delivery date.
- **Payments:** payment event month (`PaymentDateKey`).
- **Returns:** request month (`RequestDateKey`).
- **Refunds:** refund event month (`RefundDateKey`).
- **Inventory:** latest product-store snapshot; historical balances may be reconstructed from the signed movement ledger. Historical values based on current cost are **estimates**.
- **Supplier attribution:** current primary supplier on `DimProduct`, not an effective-dated historical supplier relationship.

**Critical interpretation note:** `analytics.pbi_SalesTrend.NetRevenue` subtracts **refund-month** completed refunds from **sales-month** recognized revenue. This is a calendar-activity measure, **not** a delivery-cohort net-revenue measure. Do not reconcile it to cohort-based DAX/SQL measures without first aligning date roles and filters. Consult `11_KPI_Dictionary.md` and the actual PBIX measures before asserting identical totals across pages.

The runner's configured end date is **2026-06-30**, which is a generation parameter, not proof that fact transactions exist on that date. Verify actual `MIN/MAX` fact dates independently before claiming a complete 36-month observed period.
