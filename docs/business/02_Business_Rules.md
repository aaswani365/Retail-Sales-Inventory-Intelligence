## 1. Purpose

This document defines the authoritative operational, financial, data-quality and analytical rules for Version 2 of the Retail Sales & Inventory Intelligence Platform.

The rules convert the business requirements into testable logic that will guide:

- SQL Server table design
- Keys, constraints and indexes
- Stored procedures and set-based triggers
- Synthetic-data generation
- Automated validation and reconciliation
- Analytics fact and dimension design
- Power BI measures and dashboard behaviour

Where a rule cannot be enforced by a simple database constraint, it shall be enforced through a controlled stored procedure, set-based trigger, scheduled validation or analytical control test.

## 2. Rule classifications

| Classification | Meaning |
|---|---|
| Structural | Defines uniqueness, relationships, mandatory fields or entity grain |
| Lifecycle | Controls valid status transitions and event sequencing |
| Financial | Controls prices, totals, payments, refunds, revenue and profit |
| Inventory | Controls stock balances and inventory movements |
| Temporal | Controls dates, reporting periods and event order |
| Analytical | Defines KPI inclusion, exclusion, grain and aggregation behaviour |
| Data quality | Defines validation conditions and failure handling |

## 3. Enforcement hierarchy

Rules shall be implemented using the simplest reliable mechanism:

1. Data type and nullability
2. Primary or unique key
3. Foreign key
4. Check or default constraint
5. Controlled stored procedure
6. Set-based trigger when cross-table transactional enforcement is required
7. Automated validation or reconciliation test
8. Power BI measure logic only when the rule is exclusively analytical

Business-critical integrity shall not depend only on report filters.

## 4. Global conventions

| Rule ID | Rule | Enforcement |
|---|---|---|
| BR-GL-001 | All primary surrogate keys shall be positive integers generated by SQL Server. | Identity/sequence and primary key |
| BR-GL-002 | Every table shall have a documented grain. | Data dictionary and design review |
| BR-GL-003 | Business identifiers such as SKU, OrderNumber and TransactionReference shall be unique where required. | Unique constraint/index |
| BR-GL-004 | Required business fields shall not contain null, empty or whitespace-only values. | Nullability, check constraint and validation |
| BR-GL-005 | Monetary columns shall use `DECIMAL`, never approximate floating-point types. | Data type review |
| BR-GL-006 | Monetary values shall be stored to two decimal places unless a documented exception exists. | `DECIMAL(p,2)` |
| BR-GL-007 | Quantities shall be stored as whole numbers unless a future product unit explicitly requires fractional quantities. | Integer data type |
| BR-GL-008 | Operational timestamps shall use `DATETIME2`; reporting dates shall use `DATE`. | Data type review |
| BR-GL-009 | Audit columns shall use server-generated timestamps and shall not be supplied by synthetic-data scripts unless intentionally backfilled. | Default constraint/procedure |
| BR-GL-010 | Inactive master records shall remain available to historical transactions. | No hard deletion; active flag |
| BR-GL-011 | Synthetic customer, employee and payment data shall not represent real individuals or credentials. | Generation policy and repository review |
| BR-GL-012 | All SQL-to-Power-BI business measures shall have one authoritative definition. | KPI dictionary and reconciliation |

## 17. Pricing, discount and tax rules

| Rule ID | Rule | Enforcement |

| BR-FN-005 | Item net amount equals taxable amount plus item tax amount. | Computation/reconciliation |
| BR-FN-006 | Order subtotal equals the sum of item gross amounts. | Reconciliation |
| BR-FN-007 | Order discount equals the sum of item discounts plus any valid order-level discount allocation. | Reconciliation |
| BR-FN-008 | Order tax equals the sum of item tax amounts. | Reconciliation |
| BR-FN-009 | Order net amount equals the sum of item net amounts. | Reconciliation |
| BR-FN-010 | Cost of goods sold shall use the transaction unit cost retained on each order item. | Analytical rule |
| BR-FN-011 | Profit calculations shall exclude tax from revenue when tax is treated as a pass-through liability. | KPI definition |
| BR-FN-012 | Rounding shall occur at documented transaction levels and use two decimal places. | Procedure and test |

Baseline formulas:

```text
Item Gross Amount = Quantity × Unit Price
Taxable Amount     = Item Gross Amount − Discount Amount
Tax Amount         = Taxable Amount × Tax Rate
Item Net Amount    = Taxable Amount + Tax Amount
Gross Profit       = Net Revenue Excluding Tax − COGS
Gross Margin %     = Gross Profit ÷ Net Revenue Excluding Tax
```

## 29. Acceptance conditions

This document is considered implemented when:

- Every Must-level business requirement has a mapped business rule.
- Every structural rule maps to a database object or validation test.
- Order, payment and return transitions are implemented and tested.
- Order-item, payment, refund and inventory reconciliations return zero exceptions.
- Revenue and profit definitions match between SQL and Power BI.
- Multi-row inventory operations are tested successfully.
- Fact-table grains and dimension relationships are documented.
- KPI descriptions identify their inclusion, exclusion and date-context rules.
- The final README describes only implemented and validated capabilities.

## 30. Design decisions to confirm in the next phase

The database-design phase shall confirm:

1. Whether inventory reservation will be implemented separately from on-hand stock.
2. Whether delivery and cancellation timestamps belong on the order header or an order-status history table.
3. Whether refunds will use a dedicated Refund table or payment transactions with event types.
4. Whether employee store assignment history is required or one current store is sufficient for the portfolio scope.
5. Whether product cost history requires a dedicated price-history table beyond transaction-level cost retention.
6. Whether inventory balances will be persisted or derived from movements with a controlled snapshot table.
7. Which tax rates and category exceptions will be represented in synthetic data.

Until changed through a documented design decision, the rules in this document form the authoritative Version 2 baseline.
